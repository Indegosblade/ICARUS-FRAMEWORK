# Parser Ecosystem

The parser ecosystem manages, validates, and tests parsers at scale.

## Parser contract

A parser translates a source format into the supported schema. Existing downstream
components operate on those rows according to their own mappings: FTS indexes cover
files, daemons, and atoms; STIX and diff support defined entity types; resolution
requires an atom projection. Adding a table alone does not add all integrations.

Model entities, relationships, and observations explicitly. Validate new mappings,
source trust boundaries, and failure cases with fixtures. Sanitization runs under
the configured policy and does not prove universal absence of private data.

## Building your own

Parsers are first-class to author and, crucially, to keep private:

- **In-repo** — a `BaseParser` subclass + co-located YAML manifest under
  `icarus/parsers/`. Auto-discovery registers it at import; nothing to add to a list.
- **Private (gitignored)** — files under `icarus/parsers/private/` are excluded by
  normal Git ignore behavior and public distribution rules. Force-adding or manually
  copying them can still publish them; verify the staged diff and built artifacts.
- **Distributed** — an installed package advertises parsers via the `icarus.parsers`
  entry-point group, so a third-party distribution can extend a user's ICARUS without
  touching this repo.

The manifest field is `identify.specificity_level`; it influences automatic detection
priority. Registry identity comes from the parser class's `name`, which must match
the manifest's `parser_id`. A passing 4-gate harness does not automatically promote
the declared quality tier; production metadata requires manual review. Full walkthrough:
[about/PARSERS.md](../about/PARSERS.md).

## Components

### 1. YAML Manifests

Every parser ships with a co-located YAML manifest validated by JSON Schema at load time. The manifest declares:

- **Identity** — parser_id, version, spec_version
- **Quality** — quality_tier (production/candidate/prototype/private), reliability (Admiralty A-F), default_confidence
- **Detection** — specificity_level (1-100), identification markers
- **Capabilities** — consumes (input types), produces (entity types)
- **Testing** — fixtures directory, golden output path

Schema: `icarus/parsers/schema/parser_manifest.schema.json`

### 2. Parser Registry

The registry holds all parser instances and their manifests. Registration is automatic: every concrete `BaseParser` subclass found anywhere under `icarus/parsers/` — including local-only parsers in the gitignored `icarus/parsers/private/` package — is discovered and registered at import time, and an installed distribution can advertise additional parsers through the `icarus.parsers` entry-point group. There is no hand-maintained list of parsers to keep in sync; discovery and manifest-load failures are logged rather than silently swallowed. See [about/PARSERS.md](../about/PARSERS.md) for the registration walkthrough.

When `icarus build` runs without `--parser`, the built-in parsers use one shared
sample of at most 5,000 tree entries and 4 MiB of file content, then run a
**detection contest**:

1. Every registered parser's `identify()` runs against the source
2. Parsers that return True are candidates
3. Candidates sorted by specificity (lower wins), then confidence (higher wins)
4. Winner becomes the active parser

The built-in sampler traverses the source tree once and does not follow symlinked
directories. This is not a sandbox or a limit on arbitrary trusted plugin code:
a custom `identify()` implementation can perform its own reads. Review parser
packages before installing them.
If either sample budget is exhausted, ICARUS refuses to select from incomplete
evidence and requests an explicit `--parser`. Supplying `--parser` bypasses the
detection sample.

Among matching candidates, CloudTrail (specificity 5) precedes Windows (20), which precedes generic (100). If you write a parser with specificity 10, it automatically slots between CloudTrail and Windows.

### 3. Two-Tier Catalog

- `parsers.json` — production parsers (ships with the framework)
- `parsers-devel.json` — candidate parsers (under evaluation)

Generated by `icarus/parsers/catalog/update_catalog.py` which walks all YAML manifests.

**9 parsers total** — 8 production (`parsers.json`), 1 candidate (`parsers-devel.json`):

| Parser | Tier | Specificity |
|--------|------|:-----------:|
| `cloud/aws/cloudtrail` | production | 5 |
| `macos` | candidate | 8 |
| `windows` | production | 20 |
| `linux` | production | 20 |
| `generic/json` | production | 100 |
| `generic/xml` | production | 100 |
| `generic/sqlite` | production | 100 |
| `generic/archive` | production | 100 |
| `generic/binary` | production | 100 |

The candidate `macos` parser reads embedded Mach-O entitlements with a self-contained stdlib Mach-O reader (`icarus/parsers/macho.py`) — no external `codesign` or `ldid`. Its Mach-service data represents declarations, not demonstrated reachability.

All built-in parsers share the same hostile-input boundary: source reads require
regular files and reject symlink components; direct stream readers also verify
the opened descriptor before reading. Symlinks remain visible as metadata rows
without dereferencing their targets; special files are skipped with a warning;
filesystem surrogate bytes are escaped before SQLite binding. JSON
recursion/memory failures skip one file, and compressed tar inspection has a
64 MiB decompressed-data ceiling. ZIP member listing is skipped before Python's
eager central-directory parser runs when the archive exceeds 64 MiB, its central
directory exceeds 8 MiB, it declares more than 10,000 entries, or its ZIP/ZIP64
metadata is malformed. The archive itself is still cataloged and a warning
explains why its members were not listed.

### 4. Test Harness

4 mandatory quality gates:

| Gate | What It Checks |
|------|---------------|
| **Golden output** | Entity counts match the packaged saved baseline |
| **Idempotency** | A second entity + relationship run leaves all parser output unchanged |
| **Schema conformance** | Parser only writes to tables declared in its manifest |
| **Zero-PII** | HYGEIA verify_clean passes on the output database |

```bash
icarus parser test windows
```

The compact fixture corpus and golden files ship with ICARUS, so the command
works from an installed wheel without access to the repository's `tests/` tree.

Run the harness against the installed revision to verify its declared fixtures.
Production tier is manually reviewed metadata about declared qualification; it does
not guarantee behavior for every source. Admiralty grades describe source reliability,
not software correctness. The macOS parser remains candidate-tier.

## Quality Tiers

| Tier | In Catalog | Requirements |
|------|:----------:|-------------|
| `production` | parsers.json | All 4 harness tests pass, manifest validates, real-world validation |
| `candidate` | parsers-devel.json | Under evaluation, may have known issues |
| `prototype` | No | Proof of concept |
| `private` | No | Internal use only |
